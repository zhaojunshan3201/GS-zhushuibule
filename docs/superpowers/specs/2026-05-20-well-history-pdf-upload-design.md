# 单井井史 PDF 上传与按井号展示设计

## 背景

当前 `单井井史` 页面仍是静态占位与示意内容，不能承载现场工作人员已经整理好的井史 PDF。

业务目标是把 `单井井史` 页面改造成一个可维护的井史资料页：

- 支持上传工作人员整理好的 PDF
- 支持按井号查询并自动显示对应 PDF
- 一口井显示一份当前有效 PDF
- 支持后续在同一页面继续上传更新
- 上传更新后页面自动显示最新版本

当前系统部署在局域网内，开发阶段不依赖 Oracle 实时连接，因此该能力应基于现有本地应用、`uploads` 目录和项目数据库实现。

## 目标

本次设计覆盖以下目标：

- 在 `单井井史` 页面内完成 PDF 上传、查询、预览、替换更新
- 通过井号唯一定位当前展示的井史 PDF
- 保留基础元数据，便于后续继续维护
- 文件落地本地上传目录，元数据写入数据库
- 页面在查询和上传完成后自动刷新显示最新 PDF

## 非目标

本次不做以下内容：

- 不做 PDF 历史版本对比
- 不做多版本并排展示
- 不做复杂审批流程
- 不做 Oracle 联动回填
- 不做独立后台资料管理中心

## 推荐方案

采用“文件存本地 + 元数据存数据库”的方案。

### 原因

- 文件不入库，避免数据库膨胀
- 利用项目现有 `uploads` 静态资源能力，接入成本低
- 井号、单位、区块、文件地址等元数据可查询、可更新、可维护
- 后续若要扩展备注、上传人、更新时间、历史版本，也有清晰演进路径

## 数据模型

新增一张井史 PDF 元数据表，建议命名为 `WellHistoryPdf`。

字段建议如下：

- `id`: 主键
- `wellNo`: 井号，必填，建议唯一
- `unit`: 单位，可空或必填，取决于页面录入要求
- `block`: 区块，可空或必填
- `fileUrl`: 当前 PDF 访问地址
- `storedFileName`: 系统内部保存文件名
- `originalName`: 原始上传文件名
- `mimeType`: 文件类型，固定为 `application/pdf`
- `size`: 文件大小
- `uploadedAt`: 首次上传时间
- `updatedAt`: 最近更新时间
- `remark`: 备注，可选

### 唯一约束

推荐对 `wellNo` 加唯一约束。

含义是：

- 一口井在任一时刻只维护一份当前有效 PDF
- 再次上传同井号文件时，执行“更新当前记录”

## 文件存储设计

PDF 文件保存到本地上传目录，推荐使用独立目录：

- `uploads/well-history/`

文件命名建议采用系统生成规则，避免中文文件名与重复冲突：

- `well-history-<wellNo>-<timestamp>-<uuid>.pdf`

上传新版本时：

- 写入新文件
- 更新数据库记录到新文件路径
- 删除旧文件，避免垃圾文件累积

## 后端接口设计

### 1. 上传/更新井史 PDF

接口建议：

- `POST /api/uploads/well-history-pdf`

表单字段：

- `file`: PDF 文件
- `wellNo`: 井号
- `unit`: 单位
- `block`: 区块
- `remark`: 备注，可选

处理逻辑：

1. 校验上传文件存在
2. 校验 MIME 类型为 PDF
3. 校验井号必填
4. 查数据库中是否已有该井号记录
5. 若不存在：
   - 新建文件
   - 新增数据库记录
6. 若已存在：
   - 保存新文件
   - 更新数据库记录
   - 删除旧 PDF 文件
7. 返回最新记录

### 2. 按井号查询井史 PDF

接口建议：

- `GET /api/well-history-pdf`

查询参数：

- `wellNo`

返回内容：

- 井号对应的 PDF 元数据
- 若不存在，返回 `404` 或返回空对象并标识无数据

### 3. 可选的页面初始化查询接口

若页面希望根据默认井号直接加载，可复用 `GET /api/well-history-pdf?wellNo=...`

不新增额外接口。

## 前端页面设计

页面继续保留在 `单井井史` 内，不新增独立管理页。

### 页面结构

建议结构如下：

1. 顶部查询栏
   - 单位
   - 区块
   - 井号
   - 查询按钮

2. 井史 PDF 操作区
   - 当前井号信息
   - 上传 PDF 按钮
   - 替换更新按钮
   - 最近更新时间
   - 原始文件名

3. PDF 预览区
   - 查询到文件时，直接嵌入显示 PDF
   - 查询不到文件时，显示空状态

### 查询行为

- 输入井号并点击查询
- 调用按井号查询接口
- 成功时在页面中嵌入显示对应 PDF
- 未找到时显示“该井暂无井史 PDF，请上传”

### 上传更新行为

- 在当前井号已明确的前提下，点击上传或替换
- 选择 PDF 文件后提交
- 上传成功后自动重新拉取当前井号记录
- 页面立即切换为最新 PDF

### 权限行为

建议延续项目现有权限模式：

- 所有人可查询和查看 PDF
- 有写权限的用户可上传/更新 PDF

如果当前页面内已有 `hasPermission('add')` 或 `hasPermission('modify')`，则：

- 上传按钮使用 `add`
- 替换更新使用 `modify`

## 预览方式

前端直接使用浏览器原生 PDF 预览。

推荐方式：

- 使用 `iframe`

原因：

- 接入简单
- 不新增 PDF 渲染库
- 与局域网桌面浏览器使用场景兼容性较好

降级提示：

- 如果浏览器无法内嵌预览，则显示“点击新窗口打开 PDF”

## 错误处理

需要覆盖以下场景：

- 未选择文件
- 上传的不是 PDF
- 文件过大
- 井号为空
- 查询不到记录
- 上传失败
- 旧文件删除失败但数据库已更新

处理原则：

- 优先保证数据库记录与当前新文件一致
- 旧文件删除失败只记日志，不回滚新记录
- 前端给出明确提示文案

## 可维护性设计

为了支持“以后继续维护更新”，本方案强调以下几点：

- 一井一记录，更新路径稳定
- 文件路径不依赖原始文件名
- 元数据单独存储，后续可扩展上传人、备注、标签
- 页面内可直接替换，不需要跳到其他后台

后续如果要扩展历史版本，可在此模型上演进为：

- 主表存当前版本
- 子表存版本历史

本次先不实现。

## 测试要点

需要验证：

- 上传合法 PDF 成功
- 同井号重复上传后显示最新 PDF
- 上传后旧文件被替换
- 查询不同井号时显示不同 PDF
- 查询无 PDF 的井号时显示空状态
- 无权限用户无法上传或更新
- 静态文件 URL 可直接访问

## 决策结论

本次确定采用以下实现口径：

- `单井井史` 页面按井号查询 PDF
- 一口井只显示一份当前有效 PDF
- 支持在该页面上传与替换更新
- 上传成功后自动显示最新 PDF
- 文件存本地，元数据存数据库
