# 单井井史档案与PDF识别设计

## 背景

当前 `单井井史` 页面已经具备按井号上传 PDF、查询 PDF 和预览 PDF 的基础能力，但它本质上仍是“单井 PDF 查看器”。

新的业务目标不是只展示文件，而是把这块能力升级成“单井档案页”：

- 上传井史后，资料与单个井号绑定
- 前端可通过井号模糊快速查询
- 每口井都有自己的档案页
- 档案页可持续更新维护
- 原始 PDF 仍然保留
- 后续再把 PDF 内容识别、切片、抽取为结构化资料并入库

考虑到 PDF 版式、扫描清晰度、字段分布可能并不完全统一，本次设计采用“两步走”方案：

1. 第一阶段先把 `单井井史` 做成真正可维护的单井档案页
2. 第二阶段再补 PDF 内容识别与结构化抽取能力

## 目标

### 第一阶段目标

- 把 `单井井史` 从 PDF 预览页升级为单井档案页
- 支持按井号模糊查询已有档案
- 支持查询结果列表快速选井
- 支持按井号维护当前有效 PDF
- 支持在页面内继续更新同一口井的资料
- 页面展示单井基础档案信息和原始 PDF

### 第二阶段目标

- 在保留原始 PDF 的前提下，自动识别 PDF 中的单井信息
- 把识别文本和结构化摘要存入数据库
- 档案页同时显示“结构化井史信息 + 原始 PDF”
- 后续允许人工修订识别结果

## 非目标

本次设计明确不做以下内容：

- 不做 Oracle 联动回写
- 不做多版本 PDF 对比视图
- 不做复杂审批流
- 不做跨井综合分析报表
- 不在第一阶段就追求完全自动、完全准确的 PDF 字段识别

## 总体方案

采用“原件文件 + 档案主表 + 识别结果表”的三级方案。

### 方案分层

1. 原始 PDF 文件
- 文件继续存储在本地 `uploads/well-history/`
- 便于局域网内快速访问和替换

2. 单井档案主数据
- 一口井一条主档案记录
- 记录井号、单位、区块、当前 PDF、备注等基础信息

3. PDF 识别结果
- 识别结果与某份 PDF 或某个档案绑定
- 保存抽取出的文本、摘要、解释结论、层位说明等
- 与原始 PDF 分开，便于后续人工修订

## 第一阶段设计：单井档案页

### 数据模型

在现有 `WellHistoryPdf` 基础上，新增单井档案主表，建议命名为 `WellHistoryArchive`。

#### 1. WellHistoryPdf

当前这张表继续保留，职责是保存当前上传 PDF 的文件级元数据：

- `id`
- `wellNo`
- `unit`
- `block`
- `fileUrl`
- `storedFileName`
- `originalName`
- `mimeType`
- `size`
- `remark`
- `uploadedAt`
- `updatedAt`

这张表仍然负责“文件上传与替换”的能力。

#### 2. WellHistoryArchive

新增档案主表，职责是描述“这口井的当前档案状态”。

建议字段：

- `id`
- `wellNo`
- `displayName`
- `unit`
- `block`
- `remark`
- `currentPdfId`
- `uploadedAt`
- `updatedAt`

字段说明：

- `wellNo`
  - 档案主键语义字段，建议唯一
  - 用于前端查询和后端定位
- `displayName`
  - 用于展示井名，例如 `坨37-26`
  - 允许与 `wellNo` 相同，也可单独维护更友好的展示名
- `currentPdfId`
  - 指向当前正在展示的 PDF 记录
  - 保证档案页总能定位到当前有效资料

### 关系设计

- `WellHistoryArchive.wellNo` 与 `WellHistoryPdf.wellNo` 一一对应
- 第一阶段可以采用“按 `wellNo` 绑定当前 PDF”的简单方式
- 如果未来要做历史版本管理，再逐步扩展成“一档案多 PDF 历史”

### 页面结构

`单井井史` 页面升级为完整档案页，建议结构如下：

1. 顶部查询栏
- `作业区`
- `区块`
- `井号模糊输入`
- `查询`

2. 查询联想结果区
- 输入井号关键字后，显示匹配井号列表
- 示例：
  - `坨37-26`
  - `坨37-27`
  - `雷64-12`
- 点击后载入该井档案

3. 档案主体区
- 左侧或上方：单井档案卡
  - 井号
  - 展示井名
  - 单位
  - 区块
  - 备注
  - 上传时间
  - 更新时间
  - `上传井史`
- 右侧或下方：PDF 原件完整预览

### 查询交互

- 用户输入井号关键字
- 前端调用模糊查询接口
- 返回井号候选列表
- 用户点击某一项
- 页面载入该井档案与当前 PDF

### 上传更新交互

- 当前页保留 `上传井史` 按钮
- 上传时带上：
  - `wellNo`
  - `unit`
  - `block`
  - `remark`
- 成功后：
  - 更新 `WellHistoryPdf`
  - 同步更新或创建 `WellHistoryArchive`
  - 当前页面自动刷新为最新版资料

### 第一阶段接口设计

#### 1. 模糊查询档案列表

建议新增：

- `GET /api/well-history-archives/search`

参数：

- `keyword`
- `unit` 可选
- `block` 可选

返回内容：

- 档案列表简项
  - `id`
  - `wellNo`
  - `displayName`
  - `unit`
  - `block`
  - `updatedAt`

#### 2. 查询单井档案详情

建议新增：

- `GET /api/well-history-archives/:wellNo`

返回内容：

- 档案主信息
- 当前 PDF 信息

#### 3. 上传或替换井史资料

继续复用当前上传接口：

- `POST /api/uploads/well-history-pdf`

但在上传完成后增加档案同步逻辑：

- 如果档案不存在，则自动创建 `WellHistoryArchive`
- 如果档案已存在，则更新 `currentPdfId`、`unit`、`block`、`remark`、`updatedAt`

## 第二阶段设计：PDF 内容识别与结构化抽取

### 设计原则

第二阶段不是替代原始 PDF，而是在保留原件的基础上增加“可搜索、可展示、可修订”的结构化信息层。

即：

- 原始 PDF 是事实原件
- 识别结果是可维护的派生数据

### 数据模型

新增识别结果表，建议命名为 `WellHistoryExtract`。

建议字段：

- `id`
- `archiveId`
- `pdfId`
- `wellNo`
- `title`
- `summary`
- `layersText`
- `interpretationText`
- `conclusionText`
- `rawExtractText`
- `extractStatus`
- `extractSource`
- `reviewStatus`
- `reviewRemark`
- `createdAt`
- `updatedAt`

字段说明：

- `archiveId`
  - 绑定单井档案
- `pdfId`
  - 绑定来源 PDF
- `title`
  - 识别出的标题，如 `坨37-26`
- `summary`
  - 简要摘要
- `layersText`
  - 层位、层组、解释井段等相关识别文本
- `interpretationText`
  - 解释过程或井史分析正文
- `conclusionText`
  - 结论类摘要
- `rawExtractText`
  - 原始抽取文本，便于排查识别问题
- `extractStatus`
  - 如 `pending / success / failed`
- `reviewStatus`
  - 如 `unreviewed / reviewed / corrected`

### 识别流程

上传 PDF 后流程建议变为：

1. 保存原始 PDF
2. 同步更新档案主表
3. 后台启动识别任务
4. 读取 PDF 文本
5. 提取：
  - 井号标题
  - 说明文字
  - 层位或井段信息
  - 解释/结论内容
6. 写入 `WellHistoryExtract`

### 第二阶段前端展示

档案页展示升级为三层内容：

1. 单井基础档案卡
2. 结构化识别结果
3. 原始 PDF 预览

结构化识别区建议展示：

- 标题
- 井史摘要
- 层位/井段文本
- 解释结论
- 人工修订备注

### 第二阶段查询升级

第一阶段模糊搜索先仅支持：

- `wellNo`
- `displayName`

第二阶段再扩展为可搜索：

- `remark`
- `summary`
- `layersText`
- `interpretationText`
- `conclusionText`

## 错误处理

需要覆盖以下场景：

- 井号为空
- 上传的不是 PDF
- 文件过大
- 模糊查询无结果
- 档案不存在
- 上传成功但档案同步失败
- PDF 识别失败
- 识别结果为空

处理原则：

- 第一阶段优先保证“档案可查、PDF 可看、可继续上传”
- 第二阶段识别失败不影响原始档案查看
- 识别失败仅标记状态并保留人工修订入口

## 权限设计

建议延续现有权限体系：

- 所有人可查询和查看档案
- 具备 `add` 或 `modify` 权限的用户可上传/替换井史
- 第二阶段若开放识别结果人工修订，则建议要求 `modify` 权限

## 测试要点

### 第一阶段

- 上传一个新井号 PDF 后自动创建档案
- 输入部分井号能查到匹配结果
- 点击候选井号后能显示该井档案
- 同井号再次上传后自动更新当前资料
- 不同井号能展示不同档案

### 第二阶段

- 上传后能生成识别记录
- 识别失败不影响 PDF 查看
- 结构化内容能正确显示在档案页
- 人工修订后能覆盖展示识别结果

## 实施顺序建议

推荐按以下顺序推进：

1. 第一阶段
- 新增档案主表
- 新增模糊搜索接口
- 新增单井档案详情接口
- 改造 `单井井史` 页面为档案页

2. 第二阶段基础版
- 新增识别结果表
- 打通上传后识别流程
- 页面展示结构化识别结果

3. 第二阶段增强版
- 增加人工修订
- 增加更丰富的结构化字段
- 增加多字段联合搜索

## 决策结论

本次确认采用以下路线：

- 先把 `单井井史` 做成“每口井一个档案”的可维护页面
- 支持井号模糊快速查询
- 支持当前页继续上传和更新井史资料
- 原始 PDF 继续保存和展示
- 第二阶段再做 PDF 自动识别、结构化存储和人工维护
