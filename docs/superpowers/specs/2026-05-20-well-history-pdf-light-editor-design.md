# 单井井史 PDF 轻量编辑层设计

## 背景

当前 `单井井史` 页面已经具备以下基础能力：

- 按井号查询单井井史资料
- 批量导入 `PPT/PPTX` 并自动转换为 PDF
- 在页面内稳定显示 PDF 内容
- 左侧栏承载查询条件、导入入口、导入进度与结果表

新的需求不是做一个完整的专业 PDF 编辑器，而是在现有井史阅读页上增加一层“可继续维护的轻量编辑能力”，满足工作人员日常标注、补充说明、导出成稿的场景。

关键限制已经确认：

- 不直接修改原始 PDF 文件
- 编辑后的结果只保存为当前页面可继续编辑的版本
- 同时支持下载导出带编辑结果的文件

这意味着最适合的方案不是“重写原 PDF”，而是“原 PDF 作为底稿 + 覆盖编辑层作为增量数据”。

## 目标

本次设计目标：

- 在 `单井井史` 页面右侧 PDF 阅读区上方增加工具栏
- 支持 PDF 放大、缩小、自适应显示
- 支持页内矩形标注、箭头标注、文本编辑
- 支持将编辑结果保存为当前井史页面的继续维护版本
- 支持下载导出带编辑结果的文件
- 保留原始 PDF 不变

## 非目标

本次明确不做：

- 不做真正的原始 PDF 文件覆盖写入
- 不做复杂富文本编辑
- 不做橡皮擦、撤销/重做、多人协同编辑
- 不做印章、手写签名、图片盖章
- 不做跨井号的统一模板编辑
- 不做全文 OCR 文本级定位与回写

## 方案对比

### 方案 A：PDF 底稿 + 覆盖编辑层

做法：

- PDF 继续按当前方式渲染显示
- 每一页上方叠加一个可编辑图层
- 所有标注、文字、位置、尺寸都只保存在编辑层数据中
- 导出时再把原 PDF 和编辑层合成结果文件

优点：

- 不破坏原始文件
- 编辑数据结构清晰
- 后续维护和恢复编辑状态最稳
- 和现有单井档案链路兼容性最好

缺点：

- 需要自己维护标注坐标与缩放映射

### 方案 B：先转图片，再在图片上编辑

做法：

- 先把 PDF 每页转为图片
- 在图片上叠加标注和文字

优点：

- 编辑层实现更直观

缺点：

- 清晰度与缩放质量更难控制
- 导出质量不如直接基于 PDF
- 额外增加服务端图片生成链路

### 方案 C：直接改写 PDF

做法：

- 在保存时直接把文字和标注写入 PDF 文件

优点：

- 最接近标准 PDF 编辑器体验

缺点：

- 实现复杂度最高
- 风险最大
- 一旦写坏原文件，恢复成本高

### 推荐方案

采用方案 A：`PDF 底稿 + 覆盖编辑层`。

原因：

- 最符合“只保存当前页面可继续编辑版本，不改原文件”的边界
- 可以逐步增加功能
- 对现有系统侵入最小

## 页面结构

页面维持当前左右布局：

- 左侧栏：
  - 查询条件
  - `查询井史`
  - `批量导入PPT`
  - 批量导入进度
  - 结果表
- 右侧主区域：
  - 顶部标题区：`原始井史 PDF`
  - 标题下方工具条
  - 下方 PDF 阅读区

## 工具条设计

工具条放在当前淡蓝色区域，建议分成三组：

### 1. 阅读控制

- `放大`
- `缩小`
- `自适应`

行为：

- 放大：以固定比例递增缩放
- 缩小：以固定比例递减缩放
- 自适应：重置为适合当前阅读区宽度

### 2. 编辑工具

- `选择`
- `矩形标注`
- `箭头标注`
- `文本编辑`

行为：

- `选择`：选中、移动、删除已有编辑元素
- `矩形标注`：拖拽生成矩形框
- `箭头标注`：拖拽生成箭头
- `文本编辑`：点击后生成文本框，输入文字

### 3. 操作按钮

- `保存`
- `下载`

行为：

- `保存`：保存当前编辑层数据
- `下载`：导出带标注和文字的结果文件

## 编辑交互

### 默认状态

- 页面进入时默认是 `选择/查看` 状态
- 不自动进入绘制模式

### 矩形标注

- 点击 `矩形标注`
- 在当前 PDF 页面的覆盖层上拖拽
- 生成矩形框
- 支持后续选中移动和删除

### 箭头标注

- 点击 `箭头标注`
- 从起点拖到终点生成箭头
- 支持后续选中移动

### 文本编辑

- 点击 `文本编辑`
- 在当前页面点击任一点生成文本框
- 输入文字后保存到编辑层
- 第一版支持：
  - 单色文字
  - 单字号
  - 拖动位置

不做：

- 富文本
- 多字体族切换
- 行间距排版器

### 选择与删除

- 选择模式下点击已有元素可选中
- 选中后提供简单删除能力
- 第一版可采用键盘 `Delete/Backspace` 或元素角标删除按钮

## 缩放与坐标体系

编辑层必须与 PDF 页面绑定，而不是绑定当前屏幕像素。

因此每个元素保存时使用“页面归一化坐标”：

- `x`
- `y`
- `width`
- `height`
- 或箭头的起止点坐标

这些坐标相对于 PDF 页面原始宽高保存，而不是相对浏览器窗口保存。

这样在以下情况下都能正确恢复：

- 放大
- 缩小
- 自适应
- 页面尺寸变化

## 数据模型

建议新增一张“单井井史编辑层”记录表，例如：

`WellHistoryPdfOverlay`

建议字段：

- `id`
- `wellNo`
- `pdfId`
- `elementsJson`
- `createdAt`
- `updatedAt`

字段说明：

- `wellNo`
  - 井号
- `pdfId`
  - 绑定当前 PDF 版本
- `elementsJson`
  - 保存整份编辑层 JSON 数据

## 编辑层数据结构

建议 `elementsJson` 使用统一数组结构：

```json
{
  "version": 1,
  "elements": [
    {
      "id": "uuid-1",
      "page": 1,
      "type": "rect",
      "x": 0.12,
```

## 保存逻辑

点击 `保存` 时：

1. 收集当前所有页面的编辑元素
2. 生成统一 JSON
3. 按 `wellNo + pdfId` 保存到后端
4. 若同一 `wellNo + pdfId` 已存在，则更新

保存结果：

- 原 PDF 不变
- 下次重新打开同一口井同一份 PDF 时，自动恢复编辑层

## 下载导出逻辑

点击 `下载` 时：

1. 以当前 PDF 为底稿
2. 将编辑层内容合成到每一页
3. 生成一份新的导出文件
4. 浏览器下载该导出文件

第一版建议：

- 仍导出为 PDF
- 文件名格式可为：
  - `井号-井史标注版.pdf`

## 后端接口

建议新增接口：

### 1. 查询编辑层

`GET /api/well-history-archives/:wellNo/pdf-overlay`

返回：

- 当前井号当前 PDF 对应的编辑层数据

### 2. 保存编辑层

`POST /api/well-history-archives/:wellNo/pdf-overlay`

请求体：

- `pdfId`
- `elementsJson`

行为：

- 新建或更新当前井号当前 PDF 的编辑层

### 3. 导出结果

`POST /api/well-history-archives/:wellNo/pdf-export`

请求体：

- `pdfId`
- 可选覆盖式 `elementsJson`

返回：

- 导出的 PDF 文件流或下载地址

## 前端实现建议

### 组件拆分

建议将当前 `PdfPageViewer` 升级为 3 层职责：

1. `PdfToolbar`
- 工具按钮
- 缩放状态
- 当前编辑模式

2. `PdfCanvasViewer`
- 负责 PDF 页面渲染
- 管理缩放
- 管理页容器

3. `PdfOverlayEditor`
- 每页覆盖层
- 处理标注、箭头、文本
- 回传元素数据

### 状态管理

建议维护：

- `scale`
- `fitMode`
- `activeTool`
- `selectedElementId`
- `overlayElements`
- `saving`
- `downloading`

## 异常处理

需要覆盖以下情况：

- 当前井没有 PDF
- 当前井有 PDF 但没有编辑层
- 保存失败
- 导出失败
- PDF 页数变化导致旧编辑层和新版本不一致

处理原则：

- 如果 `pdfId` 变了，就视为一份新底稿
- 不自动把旧版本标注贴到新版本 PDF 上

## 验证方式

实现后应至少验证：

1. 查询一口井后 PDF 正常显示
2. 放大、缩小、自适应能正常工作
3. 可以添加矩形标注
4. 可以添加箭头标注
5. 可以添加并编辑文本
6. 保存后刷新页面，编辑内容能恢复
7. 下载文件包含编辑结果
8. 原始 PDF 文件仍保持不变

## 实施建议

建议按以下顺序实施：

1. 工具条与缩放能力
2. 覆盖编辑层基础能力
3. 矩形/箭头/文本三种元素
4. 编辑层保存与恢复
5. 下载导出

这样可以保证每一步都可单独验证，不会把阅读、编辑、导出三件事绑在一起同时调试。
